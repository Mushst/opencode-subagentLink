commit `df6166a` plus the untracked `src/`, `tests/`, `pyproject.toml`, CI file).

## Decisions taken (2026-10-29)

The review below is kept as written. These decisions supersede it where they
differ.

| Topic | Decision |
| --- | --- |
| Name | opencode-subagentLink. Plugin ID `opencode-subagentlink` (the validator wants lowercase), display name `opencode-subagentLink`, Python module `opencode_subagentlink`, skill `/opencode-subagentlink:delegate`. |
| Distribution | Claude Code plugin, with the marketplace file in this repo. The copy-files installer, `install`, and `mcp-entry` are removed. `pip install` still works for development. |

### Evidence

- Unit tests: 47 pass on Linux with Python 3.14, also with the real `opencode`
  hidden from PATH.
- Live tests with isolated home folders and no model calls: a private server
  starts and stops cleanly; the built-in service starts on demand and is found
  again by a later command.
- OpenCode 2.2.1 behavior used by the design: `opencode service start` can be
  repeated and prints the address; `opencode service get password` prints the
  password; another OpenCode command starts a stopped service on demand;
  `opencode serve` accepts `OPENCODE_PASSWORD` or `OPENCODE_SERVER_PASSWORD`;
  a session can be created with a `subagent`-mode agent.
- End to end on this machine: the `plan` agent on the port 4096 server, through
  the plugin's MCP server, then a background `wait`. Claude was woken when it
  exited, and the outcome held only the final reply ("PONG").
- `claude plugin validate .` passes, and the installed plugin's MCP server
  connects in a fresh Claude Code process.

### Still open

- Several servers on one OpenCode database at once, for example the built-in
  service next to a server the user runs.
- Background waits that last hours, and what happens to a wait when Claude Code
  restarts.
- Real runs on macOS and Windows.
- Whether OpenCode's background service ever stops by itself when idle.
- How a `subagent`-mode agent behaves as a top-level worker. The API accepts
  it; running it was not tested.
- The GitHub repo keeps the name `Claude_OpencodeBridge`; `plugin.json` points
  there.

## How it works today

Terms used below:

- **MCP server**: a program Claude starts and talks to over stdin/stdout. It
  offers "tools" that Claude can call.
- **Skill**: a Markdown file of instructions. Claude loads it when the task
  matches its description, or when the user types its slash command.
- **Subagent**: a second Claude instance with its own instructions. Here one runs
  in the background to wait for the worker.
- **Plugin**: Claude Code's package format. It bundles skills, subagents, and MCP
  servers, and the user installs it with `/plugin`.

One delegation, end to end:

1. The user installs the Python package (`pip install .` or `uv tool install .`).
2. `claude-opencode-bridge install --register` copies the skill to
   `~/.claude/skills/` and the waiter to `~/.claude/agents/`. It registers the
   MCP server with the absolute path of the Python interpreter.
3. In a conversation, `/claude-opencode-bridge` loads the skill. Claude calls
   `setup_status`, explains the risks, and calls `configure` with two "I accept"
   flags. It asks for a project folder and calls `start`, which launches a
   private `opencode serve` on a random localhost port with a random password.
   It calls `agents`, asks which agent to make the default, and calls
   `configure` again.
4. `spawn` creates an OpenCode session, tags it as bridge-owned, and sends the
   task.
5. Claude launches the `opencode-bridge-waiter` subagent (Haiku) in the
   background. The waiter runs `python -m claude_opencode_bridge wait …` for up
   to 9 minutes, and repeats that up to 7 times. Its summary arrives in Claude's
   conversation as the subagent's result.
6. When the Claude session ends, a small watcher process sees its pipe close. It
   kills the OpenCode server and everything the server started.

The first delegation takes about seven tool calls before any work starts.

## Decisions that need your call

1. **Distribution format.** Recommendation: make the repo a Claude Code plugin
   with its own marketplace file. A new user then installs with two commands
   inside Claude Code, and Claude Code handles update and uninstall. Keep the pip
   path only for other MCP clients. Details in A1.
2. **What happens to running workers when Claude closes.** Today they stop. That
   rule is simple and easy to explain. The cost: a long task dies if the user
   closes the session or Claude restarts the MCP server. The alternative is one
   shared per-user server that outlives sessions. That server needs its own
   lifecycle (start on demand, stop when idle, find it again after restart).
   Recommendation: keep today's rule for v1, add an idle shutdown (C3), and say
   the rule plainly during setup.
3. **Which Claude clients to support.** Today the target is Claude Code (terminal
   and the desktop app's Code tab). Claude Desktop chat and Cowork load plugins
   and local servers differently and have no background completion path, so
   supporting them is separate work (likely an `.mcpb` bundle for Desktop chat).
   Recommendation: Claude Code only for v1, and remove the Desktop chat claims
   from the README.

## Keep

| Decision | Why it holds up |
| --- | --- |
| Standard library only, zero dependencies | A plugin can run the server straight from its folder with `python3`, with no install step. Keep this as a deliberate constraint. |
| One private server per Claude session: random port and password, localhost only, proxies and redirects refused | The bridge never touches the user's own OpenCode service, and credentials cannot leak through a proxy set in the environment. |
| Watcher process that kills the server's whole process group when the MCP pipe closes | Covers crashes as well as clean exits, with no polling. Tested, including a child process that ignores SIGTERM. This is the strongest part of the design. |
| Sessions tagged `metadata.bridge`, and every change checks the tag | Claude cannot steer the user's own OpenCode sessions by mistake. |
| No hardcoded agent, provider, or model; an agent's inherited default model is resolved | Works on any user's OpenCode setup. |
| Permission requests answered only with `once` or `reject`, never automatically | The correct default for a tool that runs code. |
| HTTP error bodies are not passed to Claude | They can contain keys, prompts, or private paths. |
| MCP `wait` limited to 20 seconds per call, as a fallback | Works in clients without background tasks. |
| Runtime records at mode 0600, with an ownership check | Adequate for one user on one machine. The README already says it is not a security boundary. |
| Live probe test with isolated folders | Real evidence without touching user data. Worth running in CI on a runner that has OpenCode installed. |

## Change

### A. Packaging and install

**A1. Replace the copy-files installer with a Claude Code plugin.**
Today `install` copies two Markdown files into `~/.claude`, replaces a
placeholder in them with the absolute Python path, and registers the MCP server
through the `claude` command. Two consequences:

- After a package upgrade, the bundled skill text changes, so `install` refuses
  to overwrite its own earlier files. There is no `upgrade` or `uninstall`
  command, so the user must delete files by hand.
- The absolute Python path is written into the skill, the agent, and the MCP
  entry. If that Python environment moves or is deleted, all three break.

A plugin removes both problems:

- Claude Code substitutes `${CLAUDE_PLUGIN_ROOT}` (the plugin's install folder)
  into skill text, agent text, and MCP config. The `@BRIDGE_COMMAND@` rewriting
  goes away.
- `${CLAUDE_PLUGIN_DATA}` is a data folder per plugin. Claude Code keeps it
  across updates and deletes it on uninstall. It is a good home for
  `config.json` and `runs/`.
- The MCP entry in `.mcp.json` can run the code from the plugin folder:

  ```json
  {
    "opencode-bridge": {
      "command": "python3",
      "args": ["-m", "claude_opencode_bridge", "mcp"],
      "env": {
        "PYTHONPATH": "${CLAUDE_PLUGIN_ROOT}/src",
        "CLAUDE_OPENCODE_BRIDGE_HOME": "${CLAUDE_PLUGIN_DATA}"
      }
    }
  }
  ```

  For the CLI commands Claude runs through Bash, add a small launcher script
  (for example `scripts/opencode-bridge`) that puts `src/` on the import path.
  The skill then refers to it as `${CLAUDE_PLUGIN_ROOT}/scripts/opencode-bridge`.
  Avoid a top-level `bin/` folder: claude.ai and Cowork refuse plugins that
  have one.
- Install for someone else becomes:

  ```text
  /plugin marketplace add Mushst/Claude2Opencode_bridge
  /plugin install opencode-bridge@<marketplace-name>
  ```

- `claude plugin validate .` gives a free CI check.

Trade-off: the plugin needs `python3` 3.10 or later on the PATH that Claude Code
sees. On Windows that command is often `python` or `py`. `setup_status` should
report the Python version it runs on. `uvx` is an alternative that fetches
Python itself, but it requires the user to have `uv`.

Naming: plugin names that start with `claude-` are reserved, and
`claude plugin validate` fails them. Suggested plugin name: `opencode-bridge`.
Claude Code prefixes its components with that name, for example the skill
`/opencode-bridge:delegate` and the agent `opencode-bridge:waiter`.

**A2. Your own machine needs a migration step.** The older bridge is
registered as user-scope MCP `opencode-bridge` (pointing at
`~/.codex/skills/opencode-agents/scripts/channel.py`), with the skill
`opencode-agents` and the agent `opencode-waiter`. If both versions are loaded,
Claude sees two overlapping skills and two waiters. Remove the old registration
and helpers when you switch (`claude mcp remove opencode-bridge --scope user`).

**A3. If you keep the pip installer anyway:** check for an existing
registration with `claude mcp get opencode-bridge`. Today the code parses
`~/.claude.json` directly, which is an internal file, and it sees only user
scope. Also record what was installed (path and hash), so that
`install --upgrade` and `uninstall` can replace or remove only the bridge's own
files.

**A4. Choose a license.** Without one, other people cannot legally reuse or
change the code. Add a `LICENSE` file and the `license` field.

**A5. Use one name.** Today there are six: repo `Claude2Opencode_bridge`, folder
`Claude_OpencodeBridge`, package `claude-opencode-bridge`, MCP
`opencode-bridge`, skill `claude-opencode-bridge`, agent
`opencode-bridge-waiter`. Pick one stem.

### B. First-run setup (the values a user fills in)

Today the setup values are the OpenCode path (found automatically), the default
agent (picked after discovery), and two yes/no acknowledgements. Claude learns
what to ask by reading a six-step prose list in the skill.

**B1. Make `setup_status` return an explicit checklist.** Claude then asks for
exactly what is missing, in order, and a test can check the list:

```json
{
  "ready": false,
  "detected": {"opencode": "/home/u/.opencode/bin/opencode",
               "opencode_version": "2.2.1", "python": "3.12.3"},
  "missing": [
    {"key": "consent",
     "ask": "Workers use your OpenCode permissions and provider billing, and stop when this Claude session closes. Proceed?"},
    {"key": "default_agent",
     "ask": "Which OpenCode agent should run delegated tasks by default?",
     "choices_from": "agents"}
  ]
}
```

If OpenCode is missing, that entry carries the official install link and asks
for an executable path.

**B2. Merge the two acknowledgements into one `consent`.** They are always asked
together, and Claude passes `true` for both. Two flags add a step without adding
protection. The protection that counts is that Claude explains the terms and the
user answers.

**B3. Remove the `start` tool. Start the server on the first call that needs
it** (`agents`, `spawn`, `attach`). The stated reason for a separate step is that
starting OpenCode can load project plugins, but `spawn` runs far more than that
anyway. The first delegation drops from about seven tool calls to three:
`setup_status`, `agents`, `spawn`.

**B4. Make `workspace` optional, with the MCP server's working directory as the
default.** Checked on this machine: Claude Code starts each MCP server in the
session's project folder. For this session, the old bridge runs in
`/home/aihub/projects/Claude_OpencodeBridge`. Keep the argument for delegating
into a different folder.

**B5. Optional `userConfig` in the plugin manifest** for values known before
discovery, such as an override for the OpenCode path. Claude Code asks for these
when the plugin is enabled and shows them in `/config`. Keep the default agent
in the bridge's own config file, because the user picks it after discovery and
Claude saves it with `configure`.

### C. Completion delivery and lifetime

**C1. Replace the Haiku waiter subagent with a background Bash command.** The
Python `wait` command already does all the polling without a model. The waiter
adds three things:

- A cap: 7 × 9 minutes, about 63 minutes. Longer tasks end in "waiting expired".
- A Haiku paraphrase of the worker's report. It loses detail and cannot check
  the worker's claims.
- One more file to install, and extra model cost.

In Claude Code, a Bash command started with `run_in_background` keeps running
across turns and wakes Claude when it exits. This works in the desktop app's Code
tab. So Claude can run `opencode-bridge wait …` in the background with no cap
and get the outcome when the worker finishes. Needed changes:

- Lift the 540-second cap for this mode (it exists only because foreground Bash
  stops at 10 minutes).
- Print a short outcome: status, IDs, the first lines of the final reply, and
  its size. Leave the full text to `result`, so long worker output stays out of
  Claude's context unless needed.
- Keep MCP `wait` as the fallback.

Verify this once in a real conversation before you delete the waiter. Both
approaches ask the user once to approve the Bash command.

**C2. If you keep the waiter, remove the regex checks from its prompt.** The CLI
already validates the IDs in code. Asking Haiku to check regexes adds text and no
safety.

**C3. Stop an idle server.** The desktop app keeps old sessions running. This
machine has about ten Claude Code processes running right now, each with its own
copy of the old bridge. With the new design, every session that delegated once
keeps an `opencode serve` process alive until that session ends. Stop the
private server after some minutes with no running worker, and start it again on
the next call. OpenCode keeps sessions in its database, so nothing is lost.

### D. Skill and tool text

**D1. Start the skill description with when to use it**, for example "Use when
the user asks to delegate work to OpenCode or to an OpenCode agent." Claude reads
the description to decide whether to load the skill. The current one starts with
setup.

**D2. Say each rule once.** The same warnings appear in the MCP `instructions`,
the tool descriptions, the skill, and the README. Put what a tool does in its
description, the workflow in the skill, and support limits and test status in
the README. The skill's "Diagnostics and support boundaries" section costs tokens
every time the skill loads and changes nothing Claude does.

**D3. Put a three-step quickstart at the top of the README**, then how it works,
then the limits. Today a new user reads about 200 lines of caveats before
learning how to try it.

### E. Smaller code issues

- **E1.** Every session gets the title "Claude delegated task", so they look the
  same in OpenCode's UI. Use the first line of the task as the default title.
  (`src/claude_opencode_bridge/api.py:125`)
- **E2.** `doctor` reports `ok: true` when setup has not been done.
  (`src/claude_opencode_bridge/cli.py:92`)
- **E3.** The bridge sets both `OPENCODE_PASSWORD` and
  `OPENCODE_SERVER_PASSWORD`, and the OpenCode binary contains both names. Find
  out which one `serve` reads and keep only that one. In either case, every
  command the worker runs inherits the password, so worker commands can call the
  private server. That is acceptable for one user on one machine, but the README
  should say it. (`src/claude_opencode_bridge/runtime.py:79`)
- **E4.** `Runtime.close()` can raise `TimeoutExpired` if the watcher ignores
  both the pipe close and `terminate`. Add a final kill.
  (`src/claude_opencode_bridge/runtime.py:130`)
- **E5.** A second `start` with another folder returns a summary that shows the
  first folder. B3 removes this. (`src/claude_opencode_bridge/runtime.py:67`)
- **E6.** `agents` does not filter on the agent's `mode`, so agents meant only as
  subagents can be offered as workers. I did not check how OpenCode V2 handles a
  spawn with such an agent. (`src/claude_opencode_bridge/api.py:112`)
- **E7.** The version string is in two places (`pyproject.toml` and
  `__init__.py`). Read it from one.
- **E8.** `state()` fetches the session twice on every poll.
  (`src/claude_opencode_bridge/api.py:181` and `:194`)

## Open risks (nobody has tested these yet)

- Several OpenCode servers on one database at the same time: two Claude
  sessions, plus the user's own OpenCode TUI or app. Cheap test: start two
  private servers that share one isolated data folder, and create sessions in
  both at the same time.
- One real delegated task, end to end, in a live Claude Code conversation,
  including background completion. This costs provider tokens, so it needs your
  approval.
- Process cleanup on macOS and Windows. CI runs the unit tests there, but the
  process tests skip on Windows.
